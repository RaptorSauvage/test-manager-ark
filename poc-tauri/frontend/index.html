        Server process lifecycle (the actual headline case)

        Calls the real, unmodified startServer()/stopServer()/ getStatus() from lib/serverProcess.ts - the one capability everything else in this app exists to support, untouched by this PoC until now. startServer() really does a plain OS child_process.spawn() at the real, unmodified getExecutablePath(profile)'s resolved path - no real ARK/Minecraft dedicated server binary exists in this sandbox, so "Install fake executable" writes a tiny long-running stand-in script there first (test-only, same role as "Simulate a server writing a line" above, for the process side instead of the log side). A few seconds after launch it also writes the real startup-complete log line a real ARK server would, so the real watchLogFileForMarker() picks it up and status really advances from "starting" to "running" (watch for a second server-status push event, pid unchanged, a few seconds after Start). It exits cleanly on SIGTERM, same as a real game server. Stop calls the real stopServer() shutdown sequence unmodified: RCON SaveWorld fails immediately (no ServerAdminPassword set on this fake profile, so it never even opens a socket), so it skips straight to the grace-period wait, sends SIGTERM once the grace period elapses with no exit, and confirms the real process actually died.

        Discord bot subsystem

        Calls the real, unmodified startDiscordBot()/stopDiscordBot()/ getDiscordBotStatus() from lib/discordBot.ts, which `fork()`s the real src/bot/index.ts (bundled unmodified, zero Electron imports) as its own OS process - a different real subsystem, not just the main-process logic above. Known PoC-sandbox caveat (see README's "Sidecar packaging"): when the sidecar runs as the compiled SEA binary (the default), Node's single-executable packaging makes fork() relaunch the sidecar's own embedded entry point instead of the bot script - it won't actually reach Discord either way (no outbound network to discord.com in this sandbox, and a fake token regardless), but under SIDECAR_PATH dev mode it does reach a real connection attempt and exit cleanly, which is the more informative run to try first.
